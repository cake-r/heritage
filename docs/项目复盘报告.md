## 一、专业设计者视角

### 1.1 架构与基础设施

| # | 问题 | 严重度 | 现状 | 改进建议 |
|---|------|--------|------|----------|
| 1 | **SQLite 不适合生产级并发** — 单文件写锁竞争，fire-and-forget 线程并发写入时偶发 `database is locked` | 🔴 高 | 已设 `timeout=30`，控制线程数 | 生产环境迁移至 PostgreSQL；保留 SQLite 仅用于本地开发 |
| 2 | **无数据库迁移工具** — 使用自写的 `_migrate_add_column()` 手动 ALTER TABLE，不可追溯、不可回滚 | 🔴 高 | 当前靠 `database.py` 中硬编码的迁移函数 | 引入 Alembic，每张新表生成独立 migration 文件 |
| 3 | **伴游频率控制仅内存级** — `lastCheckTime` 是模块级字典，服务重启即丢失，多实例下不共享 | 🟡 中 | 180s/45s 两级冷却 | 改用 Redis 或数据库持久化；或至少接受当前约束并在文档中明确说明 |
| 4 | **fire-and-forget 线程无监控** — 子线程失败静默，无重试机制，无死信队列 | 🟡 中 | try/except/rollback 静默吞异常 | 增加失败日志记录；关键操作（戳章/画像更新）增加重试 1 次 |
| 5 | **Model 发现机制脆弱** — `init_db()` 仅显式导入 5 个 model，其余 11 个依赖 `main.py` 的 API import 链 | 🟡 中 | CLAUDE.md 已文档化此陷阱 | 在 `database.py` 中集中导入全部 model，消除隐式依赖 |
| 6 | **CORS 配置过于宽松** — `allow_methods=["*"]` + `allow_headers=["*"]` | 🟢 低 | 开发阶段可接受 | 生产环境收紧到具体 methods 和 headers |
| 7 | **无结构化日志** — 仅有 `logging.error` 和中间件请求日志，无 trace id、无链路追踪 | 🟢 低 | 当前规模勉强够用 | 引入 `structlog` 或至少为每个请求生成 `X-Request-ID` |

### 1.2 安全性

| # | 问题 | 严重度 | 现状 | 改进建议 |
|---|------|--------|------|----------|
| 8 | **Token 存 localStorage** — XSS 攻击可窃取 token，无 httpOnly cookie 保护 | 🔴 高 | 当前仅 SPA 方案，localStorage 是唯一选择 | 增加 refresh token + httpOnly cookie 方案；或至少设置 CSP 头 |
| 9 | **密码最小长度仅 6 位** — `rules={[{ required: true, min: 6 }]}`，无复杂度要求 | 🟡 中 | 注册表单仅校验长度 | 增加至少 8 位 + 字母数字组合要求 |
| 10 | **登录无验证码/Proof-of-Work** — 虽有 rate limiter（5 次/分钟/IP），但 IP 可伪造 | 🟡 中 | `login_limiter` 基于 IP | 增加图形验证码（简单算数即可，不依赖第三方服务） |
| 11 | **密码哈希迭代次数偏低** — PBKDF2-SHA256 100,000 次，当前推荐 ≥ 600,000 | 🟢 低 | 安全性仍可接受 | 提升至 600,000 或迁移至 bcrypt/argon2 |
| 12 | **无 CSRF 防护** — 依赖 JWT Bearer 头天然免疫部分 CSRF，但非 silver bullet | 🟢 低 | SPA + Bearer token 模式天然有防护 | 保持现状，生产环境加 SameSite cookie |

### 1.3 代码质量

| # | 问题 | 严重度 | 现状 | 改进建议 |
|---|------|--------|------|----------|
| 13 | **巨型组件** — `Home.tsx` (807 行)、`Workshop/index.tsx` (555 行)、`ExhibitionHall.tsx` (预估 600+ 行) | 🟡 中 | 单个文件承载过多逻辑 | 按区块拆分：`Home/` 下拆 Hero、RecommendFeed、DailyDiscovery 等子组件 |
| 14 | **JSON 列手动序列化** — 17 张表中多处 TEXT 列存 JSON，手动 `json.dumps/loads`，无类型安全 | 🟡 中 | SQLite 无原生 JSON 类型 | 封装 `JSONColumn` descriptor 或在 model 层统一序列化/反序列化 |
| 15 | **SSE 流式代码重复** — `chat.py` event_stream 中 7 个 tool_id 各有独立 `elif` 分支，逻辑高度相似 | 🟡 中 | 每个工具分支重复 20-40 行 | 抽象为 `ToolHandler` 注册表模式，减少重复 |
| 16 | **前端硬编码色值分散** — ECharts 组件中硬编码 hex 散落各处，与 `tokens.css` 无自动同步 | 🟢 低 | CLAUDE.md 已文档化对照表 | 抽取 `chart-theme.ts` 常量文件，统一 import |
| 17 | **TypeScript `as any` 断言** — `Recognition.tsx`、`DigitalRestoration` 中 `beforeUpload as any` | 🟢 低 | 绕过 Ant Design 类型问题 | 封装 `createBeforeUpload` helper，集中处理类型转换 |

### 1.4 性能

| # | 问题 | 严重度 | 现状 | 改进建议 |
|---|------|--------|------|----------|
| 18 | **无路由级代码分割** — 所有 15 页面同步 import，首屏 bundle 过大 | 🟡 中 | Vite 默认打包 | 用 `React.lazy()` + `Suspense` 包裹路由组件 |
| 19 | **图片无优化** — 用户上传原图直接存储和返回，无压缩/缩略图/WebP 转换 | 🟡 中 | 原图存储，前端 CSS 限制尺寸 | 生成缩略图（200px/800px 两档），列表用缩略图，详情用原图 |
| 20 | **ECharts 全量引入** — `Cultivation.tsx` on-demand import 仅注册 TreeChart，但 `KnowledgeGraph` 的 3 张图各自独立注册 | 🟢 低 | 按需引入已做 | 抽取 `echarts-setup.ts` 统一注册，避免重复 |
| 21 | **无 API 响应缓存** — 遗产列表、品类列表等变化低频的数据每次请求都查库 | 🟢 低 | 数据量小 | 品类/地域/年代列表加 5 分钟内存缓存 |
| 22 | **无请求去重** — 快速切换页面时可能发起重复 API 请求 | 🟢 低 | 未处理 | 用 `AbortController` 取消前一个未完成的同类请求 |

### 2.1 首次体验（Onboarding）

| # | 问题 | 严重度 | 感受 | 改进建议 |
|---|------|--------|------|----------|

| 24 | **未登录首页空洞** — 游客只能看 4 张静态功能卡片 + Hero，没有实际内容 | 🟡 中 | "全是介绍，不能直接体验？" | 公开展馆/知识图谱入口占比加大；Hero 下方直接展示热门遗产网格 |

### 2.4 容错与恢复

| # | 问题 | 严重度 | 感受 | 改进建议 |
|---|------|--------|------|----------|
| 37 | **401 静默跳转丢失上下文** — API 返回 401 时 `window.location.href = '/login'` 强制刷新，用户刚才在看的页面/输入的内容全丢 | 🔴 高 | "我正要提交，突然跳到登录页，白写了" | 跳转前保存当前 URL 到 sessionStorage，登录后恢复；表单内容加草稿保存 |

| 39 | **上传大图无进度** — 10MB 图片上传慢，无进度条，用户干等 | 🟢 低 | "上传中...不知道还要等多久" | 使用 axios `onUploadProgress` 显示百分比进度条 |

## 四、总结

### 项目亮点（保持/发扬）

1. **架构设计扎实**：前后端分离清晰，AI 服务抽象层合理，Mock 模式的设计是亮点
2. **设计 Token 系统**：`tokens.css` + CSS 变量体系专业，暗色模式覆盖了主路径
3. **ECharts 图表质量高**：堆叠柱状图、旭日图、Choropleth 地图的专业度在同类型项目中少见
4. **CLAUDE.md 文档详尽**：架构、陷阱、模式记录全面，对新接手者有极高价值
5. **Phase 2 三模块闭环**：伴游+推荐+修习形成了完整的用户激励飞轮
6. **错误隔离到位**：AI 服务独立 try-catch、修复流水线分步容错、Mock 全局降级

### 最需要关注的三个方向

1. **用户留存**：没有新手引导，第一次来的用户不知道该做什么 → 转化率低
2. **安全债务**：Token 存储方式、密码策略、CSRF 防护需要生产级加固
3. **性能基线**：首屏加载、图片传输、SSE 连接管理在用户量增长时会暴露问题
